# 衝突編號：CONFLICT-004

## 狀態：`detected`

## 衝突描述
- **角色 A（書籍需求者 / 買家，並涵蓋家長讀者）** 需要：**全程不透露真實姓名、地址、電話**給對方使用者，僅以站內訊息與超商店號溝通；個資外洩是其核心恐懼之一（PDPA 與隱私政策也明示「絕不揭露給對方使用者」）。
- **角色 B（平台管理員）** 需要：在發生糾紛、檢舉、escrow 退款爭議時，能聯絡到當事人本人、查閱完整站內訊息與交易紀錄、必要時甚至需向第三方（金流業者、警方、稅捐機關）揭露當事人資料以履行平台責任。
- **為什麼衝突**：spec 的安全性需求一方面強調「真實姓名、地址、電話絕不揭露給對方使用者」，另一方面又要求平台保留完整審計日誌供管理員調閱、escrow 退款決策需留存證據、消保法／稅法亦要求平台能識別交易雙方身分。買家對「平台內部誰可以看到我的個資、在什麼情境下會被讀取、會不會被外流」缺乏明確答案；管理員若無存取權則無法處理糾紛，若存取權過大則違反 PDPA 最小必要原則並使買家失去信任。此衝突直接觸及法遵（PDPA、消保法）與平台信任，屬於高敏感度議題。

## AI 分析
此衝突屬於 **隱私權 vs 平台治理** 的張力，是所有 C2C 交易平台都會面對的法遵與信任課題。在台灣的 PDPA 與消保法框架下，問題更複雜：

1. **PDPA 最小必要原則**：平台收集的個資只能用於「告知目的」內，管理員調閱個資需有正當事由與紀錄。
2. **角色內隔離**：spec 目前未區分「一線客服」「資深客服」「法遵 / 法務」對個資的存取層級；若全體後台人員都能查閱真實姓名／地址／電話，違反最小化原則。
3. **使用者知情權**：買家有權知道「在什麼情況下、由誰、為什麼讀取了我的個資」，但 spec 目前僅有審計日誌但無使用者端可視化。
4. **糾紛場景的張力**：當買家檢舉「賣家寄錯書」時，管理員是否需要看到買家姓名才能處理？多數情境下站內訊息與訂單編號已足夠，真實個資只在升級到法律程序時才需要。
5. **第三方揭露**：警方、稅捐機關依法調閱個資時，平台需有明確流程與通知機制。

## 解決方案
- [ ] 方案 1（優先滿足角色 A，買家隱私）：管理員後台預設**遮蔽**真實姓名、地址、電話（顯示為 ****），僅顯示訂單編號、暱稱、超商店號、站內訊息；若需查閱原始個資需「具名申請 + 事由說明 + 主管二次核准 + 自動通知當事人」；個資存取本身亦寫入審計日誌並可由使用者透過「我的個資存取紀錄」自助查閱。
- [ ] 方案 2（優先滿足角色 B，管理員效率）：管理員後台預設可直接查閱所有當事人資料以加速糾紛處理；僅以「事後審計日誌 + 主管定期抽查」作為節制機制；對使用者僅在隱私權政策中概括告知「平台人員為處理糾紛得查閱個資」。
- [ ] 方案 3（折衷分級）：(a) 將後台角色分層為「客服一線（只看暱稱、訂單編號、站內訊息，個資全遮蔽）」「資深客服（可在個案點開個資，自動寫入審計日誌）」「法遵專員（可匯出個資供第三方揭露，需主管核准）」；(b) 任何個資存取都自動寫入審計日誌，並在使用者個人頁可查；(c) 第三方揭露（警方、稅捐）建立 SOP 與當事人通知機制（除法律明文禁止通知者外）；(d) 隱私權政策明確列出「平台人員可在哪些情境下存取哪些欄位」。
